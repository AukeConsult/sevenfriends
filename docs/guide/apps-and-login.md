# Android / iPhone / Windows apps, login methods, first-time setup

Part of the project guide (moved out of `CLAUDE.md`; text unchanged). Read this before changing this area.

## Login methods and console setup
- Phone sign-in (per the Firebase guide): `localhost` is **not allowed** for real SMS (use the emulator, whose log prints the code with the reCAPTCHA check switched off, or up to 10 **fictional test numbers** with fixed codes under Authentication → Sign-in method → Phone → "Phone numbers for testing"). The deployed domain must be under Authorized domains. Phone alone is less secure than the other methods (a number can change hands), so it is offered next to Google / email; the phone page tells people that a text is sent and message rates may apply.
- Google, email/password, email link, phone SMS. People are reachable by their email or phone even when unverified; their friends are told (see People who have not verified).
- **Nobody has to be verified to add a friend or to be added.** Verification only decides what the other side is told (see People who have not verified). A phone login has no email and is confirmed by the SMS code; Google and email-link logins arrive with a verified email. The account document keeps `emailVerified` and `verifiedPhone`, written from the login token at every login, and `GET /profile` returns `emailVerified` / `phoneVerified`. The Verify buttons only appear for what is not verified yet.
- Firebase console: Authentication → enable **Google**, **Email/Password** (with **Email link** switched on) and **Phone**; add your domain under Authorized domains. Phone sign-in needs the **Blaze plan**, costs per SMS, and SMS region policy should allow your countries.
- Emulator: reCAPTCHA is disabled and SMS codes are printed in the auth emulator log; email links are printed there too.
- After backend changes: `npm --prefix functions install`, restart emulators, `firebase deploy --only firestore` (rules and indexes), then deploy functions.
- Known gap: email-link, SMS and rules tests are not automated in the cloud (needs the emulator); they are build-verified only.
- **Never write `firestore.rules` in place while the emulator runs** (a truncating write can be read as an empty file; the emulator then fails every database request with "Rules content empty"). Save the file in one step; if it happens, save the file again and look for "Rules updated" in the emulator log.

## Android app (`android/`)
A Capacitor wrapper that loads the live web app (`frontend/capacitor.config.json`, `server.url`). `npm run android:sync` after changing the
config or plugins; `npm run android:open` for Android Studio. Details and what is still missing: `android/README.md`. Never edit the generated
files in `android/` (capacitor.settings.gradle, app/src/main/assets); the native code of our own goes in `android/app/src/main/java/io/sevenfriends/app`.

## iPhone app (`ios/`)
Same wrapper as `android/` (`npm run ios:sync`, `ios:open` on a Mac, `ios:config` for `GoogleService-Info.plist` from the key in `.env`). Details and what
is missing: `ios/README.md`. Generated files (`Package.swift`, `App/App/public`) are not edited; our own native code is in `ios/App/App`.

## Windows app (`windows/`)
A native .NET 8 (WPF) app with the WebView2 control that shows the live web app (`AppUrl` in `windows/MainWindow.xaml.cs`, the same address as `server.url` in `frontend/capacitor.config.json`: change both together). `npm run windows:run` to try it, `windows:publish` for the self-contained exe, `windows:installer` (Inno Setup 6) for `windows/installer/output/SevenFriendsSetup.exe` (per user, no admin). The window closes to a **tray icon** (the app keeps running; menu Open / Start with Windows / Quit; the installer can start it hidden with `--tray` at sign-in) and shows the web app's notifications as Windows toasts. Details and what is missing (push when the app is not running = WNS, signing, auto-update, Google sign-in in an embedded window; not yet compiled on Windows): `windows/README.md`. The icon `app.ico` is made from `frontend/public/icons/icon-512.png`.

**Apps for download**: `scripts/publish-download.mjs` puts a finished file in `frontend/public/downloads/` (git-ignored; `npm run windows:release`; Android: the Gradle tasks `publishApk` / `deployApp` in `android/app/publish.gradle`); `deploy:hosting` publishes it and the Install page shows **Download for Windows** / **Download the Android app** only when the file exists (`InstallApp.exists`: a HEAD request that is not answered with html). The apk is debug-signed (not for Google Play).

**Welcome page** (`/welcome`, public): shown before sign-in to anyone not running the installed app (`WelcomeService.shouldShow()`, used by `authGuard`); same top (`app-hero`, four points). It offers **no install**: signed out, the one way on is the web app ("Continue in the browser", or "Sign in or create an account first" when an invitation waits), which opens `/login`; signed in, "Continue to your home page". "Continue in the browser" remembers 30 days (`welcomeUntil`) unless a friend invitation is waiting. For a code link the page shows **who invites**: the name and the address with its middle hidden (`l***@gmail.com`), from the public `GET /api/invite-public/:code` (`FriendLinkService.inviter`, shown by `app-inviter` as a white pill right under the headline of EVERY welcome page, `/welcome` and the Friends, Buddy, Work and Family pages; the full address and phone stay behind the sign-in at `/invite/lookup/:code`). The sign-in page has "I have an invitation" (paste a link, code, email or phone: `FriendLinkService.use`), and the Android app opens links of the website (`MainActivity.pathOfWebsiteLink`). Install lives in Settings > Install. Details and the strategies: `docs/invite-install-login.md`.

## First-time setup (`/setup`, `frontend/src/app/setup/`)
- The **welcome page** (signed out, not the installed app) shows who invites (for a code link) and ONE button on to the web app (`/login`); no install options. With a friend link waiting the button says "Create my account" and the login page opens at **Create account** (`Login.mode` starts as `signup`; the toggle goes to sign-in).
- **After creating an account** the person lands on **Home** (`AuthService.landingPath()` sets `setup` to `'start'`; it never goes to `/setup` by itself). Home shows the "Finish setup" notice for `start` and `skipped`, and keeps it until the wizard ends with Finish (`done`); the wizard still counts as the first time for `start` (message text hidden on the lock screen).
- **An invitation decides the circle:** a signed-out visitor with a waiting link goes on in the circle the link invites into, whatever circle the browser was in (`FriendLinkService.enterCircleOf`, used by the welcome button and `app-next-step`; it calls `ActiveCircleService.choose`, no reload). A new account made from a link for another circle also switches to that circle before the request is sent (`AutoInviteService`), so there is no "this invitation is for another circle" page in between; only an existing account still gets that message on `/friends/join`.
- **A friend link answers itself for a brand-new account:** creating the account is the yes. `AutoInviteService.run()` (called from `app.ts` once, when `AuthService.takeNewAccount()` is true) looks the code up and sends the friend request to the inviter at once (`friends.add`), then clears the link; nothing is asked. The inviter gets the usual ping and accepts as usual, so seats and the waiting list work as before. Anything unusual (a link for another circle, the inviter has already asked me, any failure) falls back to the confirm page `/friends/join`, which is also what an existing account sees.
- **A new account, or a different person than the last one who signed in on this browser, starts clean** (`AuthService.clearLocalSession`, called from `finishLogin`; the last person is `sf-last-uid`): `UiPreferencesService.clearAccountChoices()` (every local choice back to its default except the waiting friend link, the welcome choice, language, theme and text size), the desktop-notification switch (`DesktopNoticeService.reset()`: off), the small remembered views (`sf-sleep-view`, `sf-checks-hidden-until`) and the tab's session storage. The same person signing in again keeps theirs (for example ready-made messages kept on this device only). The keys of the device are not touched; the browser's own notification permission cannot be reset from the page.
- In the wizard the **name is required** (the about-you step's Next stays off while it is empty) and every step has **Back / Next** (Finish on the last) both in the top bar and at the foot of the page.
- The setup wizard (`setup/`) is short: **1 about you** (name, picture or icon; the device's country is saved, colour / country / language are under Settings → Profile), **2 the first friend** (the add page returns to this step), **3 notifications** (`notice-controls`; where notifications need the app, a line says so; for a NEW account the text of a message is hidden on the lock screen: `hideText` is switched on once, the switch in the list turns it back), and **install the app** last (there is no key step: the lock is made silently, see below) where it is not installed. A computer browser: profile, friend, notifications, install. A phone browser: profile, friend, install (notifications follow in the app). Inside the app: notifications, friend. **Finish** is always at the top right of the page; every step has "Do it later" (`setup` becomes `skipped` and Home shows a "Finish setup" bar). Sounds, text size and theme, the email check (a bar on Home), microphone and camera (asked the first time they are used) are no longer steps: they are under Settings. Signing out sets `setup` back to `new`.

- **The lock is made silently** (`docs/design/default-key.md`, step 1): the first time a person signs in on a device with NO key at all (none on this device, none published), `KeysService.refresh()` calls `makeIdentity()`: a lock key (RSA-OAEP 3072) and a signing key (ECDSA P-256), both unextractable, are saved in the key store, published with `POST /keys` (`signKey` next to `publicKey`), and version 1 of the signed device list is published with `POST /keys/list` (`core/device-list.ts`). Nothing is shown and there is no backup or secret words yet (a rescue code comes with step 5). It is tried once per person per start of the app; on failure the device is put back as it was and the key is retired. A person whose key is published but not on this device (`elsewhere`) or who has an older key is never touched: old keys keep working and get a signing key only when they rotate. Home still shows "Privacy lock is off" (`lockOff`) when no key exists, now only when the browser cannot keep one.
- **A friend's new key:** `key-changed-band` (under the header of a friend's page) accepts a friend's first keys silently (trust on first use, fingerprints kept on this device in `localStorage` `sf-pinned-keys:<friendId>`) and asks about a later one: "Did you change phone?" with "Yes, it is Leif" (remembers it) and "I am not sure" (opens Locking → Advanced to compare the codes). It only asks: sending is not stopped.
