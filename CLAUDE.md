# Seven Friends – project guide

An app for staying in contact with your 7 closest friends.

## Structure
- `frontend/` – Angular app (standalone components, signals, Bootstrap 5 + SCSS), hosted on Firebase Hosting.
- `functions/` – Node.js + TypeScript Express backend, deployed as the Firebase Cloud Function `api` (served at `/api/**`).
- `firebase.json` / `.firebaserc` – Firebase config. Link the project with `firebase use <project-id>`.

## Pages
- `/` **Notifications** (home): a quiet page with incoming friend requests and unread messages. No banner, light styling; shows "All quiet" when empty.
- `/friends` **Friends**: the friend circle (7 slots), add/remove friends, pending/confirmed badges.
- `/friends/:id/invite` **Invite your friend**: full-screen page shown after adding somebody who has no account yet. It shows the address / number and the message so the sender can **verify them first**, then **Send email / Send SMS**, **Not now**, or "wrong address, remove and add again".
- `/friends/add` **Add a friend**: a full-screen form that ends with **Cancel** and **Send friend request** (opened from an empty seat on the Friends page).
- `/friends/:id` **Conversation**: the message feed with one confirmed friend (click a confirmed contact, or the chat icon on its card, or Open on a message on Home). Incoming messages appear at once while the page is open (live, see Live updates); a slow 30-second refresh is only a safety net.
- `/friends/:id/image` **Send an image** and `/friends/:id/video` **Send a video** (one page, `add-media`, the route has `data: {kind}`): full-screen page opened from the image or video icon in the message field of a conversation: **Take a photo** / **Record a video** and **Choose an image** / **Choose a video**, a preview (picture or a video with controls) with its name, size in pixels, length and bytes, an optional text (the caption), **Cancel** and **Send**. See "Media cache" (app side).
- `/friends/:id/audio` **Send a voice message** (the same `add-media` page, `data: {kind: 'audio'}`): opened from the microphone icon in the message field: **Record a voice message** (the recorder is on the page, on phones too) and **Choose an audio file**, a player to listen before sending, name · length · bytes, an optional text, **Cancel** and **Send**.
- `/media/:ownerId/:objectId` **Image, video or audio**: full-screen viewer of an image, a video or an audio message of a message (opened from a friend's image in the feed, from the **⤓** button on a video or an audio message, or **Open** on any of my own); the title is the file name, under it the type and size, and a **Download** button that saves the file on the device under its file name (an `<a download>` on the bytes already read from the server; an extension is added from the type if the name has none).
- `/pending` **Pending**: incoming friend requests that wait for a free seat (all 7 seats taken). With a free seat they show as a pending friend on `/friends` instead.
- `/profile` **Profile**: account details, an editable **name**, phone and social accounts, all **autosaved** (no Save button, see Profile); reached from the dropup on the bottom menu (also holds Log out).
- `/profile/picture` **Your picture**: full-screen page to upload a profile picture (see "My own picture").
- `/sound-and-notifications` **Sound and notifications** (the page is called this everywhere in the app; the component folder is still `frontend/src/app/settings/`): full-screen page (dropup menu on Profile → "Sound and notifications") with desktop notifications on/off and where the user picks the sound for each of the three events (new message, friend request, answer to my request). Each event shows its chosen sound as a row that opens the full-screen page `/sound-and-notifications/:event` (`frontend/src/app/sound-picker/`; never a drop-down, which can open outside the screen) listing No sound, Ding, Chime, Bell, Pop, Marimba, Soft note and the jingles (the jingles are listed first, under "Seven Friends jingles"). Choosing a sound plays it; every row has one Play button that becomes a Stop button while its tune plays (one tune at a time: pressing it again stops the tune, another tune replaces it); the choices and the volume are saved on the account.
- `/delete-account` **Delete my account**: full-screen page that erases the user and everything shared with others (see Deleting my account).
- After **creating an account** (any login method) the app opens `/profile` so the person can fill in their details; later logins go to Home. (`AuthService.landingPath()`.)
- `/login` **Login**: Google, phone (SMS code, `/login/phone`), email link (`/login/email`, finished at `/login/link`) and email/password (a verification email is sent at sign-up). `/verify-phone` lets a signed-in user verify a phone by SMS (Profile).
- Bottom menu (always visible when signed in): Home, Friends, **Me** (dropup: My profile, Sound and notifications, Log out). The third item is called "Me", not "Profile".

## Mobile first (important)
**The default use of this app is on a mobile phone.** All UI work must follow this:
- **Every function is a full-screen page.** This is a mobile app, so the standard is: a function (adding a friend, a conversation, the profile, ...) gets its own page and route that fills the screen, not a pop-up.
  - **No pop-ups:** no modals, dialogs, bottom sheets, overlays or `window.confirm` / `alert` / `prompt`. A quick confirmation (like delete) is an **expandable frame inside the page**, under the thing it is about.
  - A sub-page has a **sticky top bar** with a back arrow and the title (see `chat` and `add-friend`). A form page **ends with Cancel and the main action** (for example "Send friend request"). Leave room at the bottom for the bottom menu.
  - The only floating element is the small "Me" dropup in the bottom menu: it is navigation (My profile, Sound and notifications, Log out), not a function.
  - New function checklist: a component in its own folder, a route in `app.routes.ts` (put fixed paths like `friends/add` **before** parameter paths like `friends/:id`), guarded with `authGuard`, and a link or button on the page it comes from.
- Design and build for a ~360–430px wide portrait screen first; add `min-width` media queries to adapt up to tablet/desktop, never the other way around.
- Touch targets at least 44x44px; no hover-only interactions.
- Use the bottom tab bar for primary navigation; keep key actions reachable with one thumb.
- Respect safe areas (`env(safe-area-inset-*)`) and use `100dvh` instead of `100vh`.
- Keep the viewport meta tag (`viewport-fit=cover`) in `frontend/src/index.html`.
- **The bottom menu is always shown when signed in, so every page needs room under its content** (about 4.5rem plus the safe area): `.sf-narrow` already has it; a page with its own layout must add the same bottom padding.
- Test every change in a mobile viewport (browser devtools device mode) before desktop.
- Keep the bundle small and avoid heavy dependencies; assume a slow mobile connection.

## Styling: Bootstrap + overall stylesheet
- **Only 4 font sizes exist** (`src/styles.scss`, `:root`): `--sf-fs-description` (the smallest: descriptions, hints, notes, labels, badges, small buttons), `--sf-fs-text` (normal text, inputs), `--sf-fs-title` (titles of sections, cards, pages) and `--sf-fs-heading` (big headings). They scale with the view size (the root font size). **Never write another font size**: use one of the four variables or the classes `.sf-fs-description`, `.sf-fs-text`, `.sf-fs-title`, `.sf-fs-heading` (Bootstrap's `small`, `h1`–`h6`, `btn-sm`/`btn-lg`, badges and form texts are already mapped to them). Big decorative glyphs (the logo "7", the back arrow ‹, the moon, a big initial) are pictures, not text, and may have their own size. Changing the look of all small texts means changing ONE variable.
- Use **Bootstrap 5** (CSS only, loaded in `angular.json` before our styles; no Bootstrap JS) for layout and components: grid (`row` / `col-*`), `btn`, `form-control`, `alert`, `badge`, `card`, `nav`, utilities (`d-flex`, `gap-*`, `text-secondary`, ...). Prefer Bootstrap classes over hand-written CSS.
- **`frontend/src/styles.scss` is the overall stylesheet** (loaded after Bootstrap). Brand colours, font sizes, dimensions and the Bootstrap theme overrides live there as CSS variables. Change values there, not per component. Radio buttons, checkboxes and switches that are not selected have a dark 2px border (`.form-check-input:not(:checked)`), so they are always visible.
- **No page-local or component-local CSS.** There are no component `.scss` files and components have no `styleUrl`: ALL styles live in `styles.scss`, as the standard `sf-*` layout classes, and templates only use those plus Bootstrap utilities. Standard classes: `sf-bar`/`sf-back`/`sf-bar-title` (sub-page top bar), `sf-narrow` (form column), `sf-page` (+`sf-page-first` when no bar above), `sf-content`, `sf-feed`, `sf-landing`, `sf-page-head`, `sf-hero`, `sf-heading`, `sf-section`, `sf-hint`, `sf-field`, `sf-actions`, `sf-list`/`sf-list-item`/`sf-list-text`, `sf-avatar`(`-sm`, `-empty`), `sf-photo`, `sf-choices`/`sf-choice`, `sf-summary`, `sf-expand`, `sf-card`, `sf-profile`, `sf-menu*`, `sf-composer`. A new page reuses these; a new look is added to `styles.scss` as a new standard class (rem units and the variables only, never fixed `px` for sizes or fonts). Every routed page is `display:block; min-height:100dvh` (one rule on `router-outlet + *`); the page classes keep room for the always-visible bottom menu.
- The whole app is at most **1000px wide** and centred (`--sf-max-width`). Fixed elements (tab bar, bottom sheet) obey the same limit.

## Connection rules (friend requests)
These rules are implemented in `functions/src` and covered by the tests in `functions/test` (see Testing). Change a rule in code AND here AND in a test.

### Structure
- `user-account/{uid}/friend-circle/{circleId}`: one document per circle, `{ name, type }`. Only the default circle "My friends" (id `default`, type `friends`) exists: every user gets it, and there is no endpoint to create more (add one when another circle type is really built).
- `.../friend-circle/{circleId}/friends/{id}`: my friend entries. `user-account/{uid}/friend-request/{id}`: requests that reached me. `user-account/{uid}/incoming-signal/{id}`: pings that somebody added me (see Pings). `user-account/{uid}/messages/{id}`: messages.
- **Seats:** max **7** entries per circle (pending, confirmed and rejected all use a seat). The 8th add is refused (409).
- **One connection, one id:** the requester's entry id = the request id = the other person's entry id (also stored as `connectionId`). Each side can always find the other.

### Adding a friend
- **The name is optional**; **an email or a phone number is required**: without a name the email (or phone) is shown, and once the friend confirms they are shown by the name of their account (the entry remembers `nameGiven`; a typed name is always kept). **An email or a phone number is required** (so the friend can be found). The add-friend page shows only these two search fields (social accounts are not asked for there; they are only contact info on a Profile). Email and phone are validated.
- Adding writes ONE pending entry in the requester's list. **No request and no seat** is created on the other side (that only happens in their check). If the person already has an account, they also get a **ping** (see Pings).

- **A message can be added** to the request (optional, max 500 characters). It is stored on the entry, copied to the other person's request, and shown with the request on Home and on the waiting-list page. It is also part of the invitation below.

### Inviting somebody who is not a user yet
- When adding a friend, if **nobody has an account** for that email or phone (the same search as the pings), the new entry gets `invite: { to, sentAt: null }` **when an email was given**. **There is no SMS invitation**: text messages are only used for login codes (Firebase sends those itself; there is no SMS provider, no Twilio). A friend added only by phone number gets no invitation offer (`invite` is null; nothing can be sent), and the sender can add an email instead. `Friend.invite` is null for people who already have an account (they get the request in the app) and once the friend has signed up.
- **Nothing is sent when the request is added.** The app opens the verify page (`/friends/:id/invite`); only `POST /circles/default/friends/:id/invite` sends. It is refused (409) when the friend has no invitation, was invited already (**once per friend**), or has signed up in the meantime; 429 after `MAX_INVITES_PER_DAY` (20) invitations in 24 hours; 404 for somebody else's friend.
- Sending writes to an outbox in the same transaction that marks `sentAt`: `mail/{id}` (the format of the Firebase Trigger Email extension), which the `sendMail` function sends through your own mail server (see "Sending email"). The document carries `fromUid`, is closed to clients (no rules) and is **erased with the sender**.
- The text holds the sender's name, the message and where to sign up with that same email address. The friend then finds the request through the normal check once they have signed up with it.
- Known trade-off: the add response tells the sender whether the address already has an account (needed to decide whether to offer an invitation). The 20 per day limit and the verified-sender rule limit abuse.

### People who have not verified their email / phone
- **Everybody is reachable**, verified or not: a request arrives whether the address was verified or not. The cost of that (somebody could sign up with your friend's address without proving it is theirs) is paid by **telling the other side**:
  - **Friend card / request card**: the friend entry carries `unverified: ("email" | "phone")[]` and a request carries `fromUnverified`, from the other person's account (`unverifiedDetails` in `validation.ts`): `[]` as soon as ONE detail is verified (a verified email or an SMS-confirmed phone), otherwise every detail the account has. The card says "{Name} has not verified their email / phone, so we cannot be sure it is really them". It shows for both sides, pending or confirmed, until they verify. No invitation is offered (they are a user already).
  - **Front page banner (for the unverified person themselves)**: **closed by default: only a small amber "!" mark (`.sf-mark`, centered) shows that something should be done; tapping it opens the note** (with the Verify button), tapping it again closes it. The note is shown only when nothing of theirs is verified: "Your email is not verified. You still receive friend requests, but your friends are told that you have not verified, because someone else could be using it", with a Verify button to the Profile.
- Known trade-off: somebody who signs up with an address that is not theirs, without verifying it, receives the requests meant for it; the sender's card shows the warning, so they can drop the friend. The requester also learns whether an account exists for an address.

### How the other person finds the request (the "check")
- Runs when they open/tap Home, or open Friends or Pending, or when a ping arrives while the app is open (`POST /api/notifications/check`; overlapping runs are shared).
- It matches *their* email and phone against everyone's **pending** entries, verified or not (see "People who have not verified"):
  - email: case-insensitive. Phone: last 8 digits (`+47 926 55 195` = `92655195`), from the login (confirmed) or the number typed on the Profile. Social accounts never match anyone.
  - Account fields: `emailLower` (the address, any), `emailVerified`, `phoneKey` (confirmed number, else the typed one, kept up to date by the Profile), `verifiedPhone` (only when confirmed by SMS; then the number cannot be edited on the Profile).
- Ignored: their own entries, entries that are not pending, entries already linked to another user, entries that are themselves seats for an incoming request, and any request that already exists (any status).
- A match creates the request (same id) in their inbox and links the requester's entry (`linkedUid`).

### Pings (incoming signals)
- When a friend is added, the backend looks for accounts the new entry points at (same matching as the check: email and phone, verified or not; the person adding is left out) and writes a ping for each: `user-account/{uid}/incoming-signal/{connectionId}` = `{ connectionId, time }`. **A ping holds no names or details.** An entry that points at two accounts pings both. A refused add (full list) pings nobody.
- The check reads the pings at its start and deletes exactly those when it has finished (if the check failed they stay; a ping that arrives meanwhile stays for the next check). A ping is only a wake-up: the request itself only ever comes from the check.
- A ping goes away with its entry: when the requester deletes the entry, when the entry is merged into a connection (both added each other), and when it is dropped as a duplicate.

### Live updates (one common service in the frontend)
`core/realtime.service.ts` is the only place that listens for changes, with Firestore realtime listeners (`onSnapshot`) under the signed-in user's own account. It starts at login and stops at sign-out. The Firestore SDK is loaded after login (a separate download, not in the first one).
- **A ping** (new document in `incoming-signal`): run the ordinary backend search (the check) and reload the friends, so the request shows in the incoming events on Home (and as a pending seat on Friends).
- **A change in my friend list** (any change of an entry under `friend-circle/default/friends`, after the first snapshot): the friends are reloaded at once (changes arriving together are one reload). This is how the **sender hears the answer**: when the other person confirms or rejects, their entry in my list changes, the Friends page updates live, and a desktop notification says "X accepted / rejected your friend request". The same listener catches a friend deleting me or a request being linked.
- **A friend deleting me** is the same change (my entry disappears): the Friends list loses them live and a desktop notification says "X removed the friendship".
- **Listeners restart themselves**: if a listener breaks (connection lost, rules reloading), it starts again after 5 seconds, so live updates do not silently stop until a page reload.
- **A new message** (new unread document in `messages`):
  - if the feed of the person who wrote is **open**, the Chat page shows the message at once and marks it read (it does not turn up on Home);
  - otherwise the search runs, so the message shows in the incoming events on Home.
- Only **new** documents count; documents going away (the backend deleting a handled ping, a message being marked read) never start a search. What is already there when the listener starts is shown once.

### Sound (stage one: while the app is open)
- `core/sound.service.ts` plays a short sound, made in the browser with the Web Audio API (no sound files). Three events, each with **its own chosen sound** (Settings page): **message** (default Ding), **request**, somebody added me (default Chime), **answer**, the other person confirmed or rejected my request (default Soft note). The choices are Ding, Chime, Bell, Pop, Marimba, Soft note, or No sound (that is also how a sound is turned off).
- Triggered only by the realtime service, for **new** things (what was there at start is not announced), and **not for a message in the conversation that is open**. My own messages never make a sound.
- Browsers only allow sound after a first tap/click/key press on the page; before that the sound is silently skipped (it is unlocked at the first interaction).
- **The choices belong to the ACCOUNT**, so they follow the person to every device: `GET /api/preferences` (`{ sounds: { message, request, answer, volume } | null }`) is read when somebody signs in, and `PUT /api/preferences/sounds` saves all four values (validated: a built-in id or `file:<plain file name>`, volume a whole number 0–100; all or nothing) about 0.6 s after the last change (`functions/src/preferences.ts`, stored in `soundPreferences` on the user-account document, so it is erased with the account). `localStorage` (`sf-sounds`, `sf-volume`) is only a **copy for a quick start and offline**; it is cleared at sign-out, so the next person on the device starts with the defaults. An account with no saved sounds takes over the device's choices the first time (migration). Notifications (desktop switch, push) stay per device.
- **Volume**: a 0-100 % slider on the Sound and notifications page (default 80 %, louder than the first version; saved on the account with the sounds). The volume is applied on a curve (`MAX_GAIN * (volume/100)^2`), so the slider feels even; changing it plays nothing, but a tune that is playing gets louder or softer at once (a master gain for built-in sounds, `audio.volume` for jingles). The device's own volume still applies on top.
- **Music jingles**: drop an audio file (`.mp3`, `.wav`, `.ogg`, `.m4a`, `.aac`) in **`frontend/public/sounds/`** and it appears under "Jingles" in every sound drop-down on the Sound and notifications page; the file name is the label (`Happy_birthday.mp3` → "Happy birthday"). `scripts/sounds-manifest.mjs` (`npm run sync:sounds`, run by itself before frontend start / build / watch and so before `firebase deploy`) writes `frontend/public/sounds/sounds.json` (generated, not committed); `SoundService.jingles` reads it. A jingle choice is stored as `file:<file name>` on the account, so **do not rename or delete a file people may have chosen** (they then hear nothing until they choose again). It plays through an audio element at the chosen volume (same curve), one at a time, and is stopped after 20 seconds. Keep jingles short (a few seconds up to about 15) and not huge (they are downloaded when played, also on phones); use only music you may use (they are public). `frontend/public/sounds/README.md` explains this and is not deployed.
- To add a sound: add it to `TUNES` in `sound.service.ts`; the Sound and notifications page lists it by itself.
### No notifications inside the page
- **Notifications are shown on the PC screen (the system's own notification, outside the browser), never as a card or pop-up inside the browser page.** There is no toast component. The page itself just updates (lists, badges, the title count); the sound plays. A new kind of notification goes through `DesktopNoticeService.show` (see below), not through an in-page alert.

### Getting attention while the app is in the background
- **Tab title** (`core/attention.service.ts` + `core/app-title.strategy.ts`): the title shows how many things wait, `(2) Friends – Seven Friends` (unread messages + friend requests that have a seat to confirm). While the tab is in the background it flashes between that and "💬 New in Seven Friends". The page titles still come from the route `title`s; the title strategy hands them to the AttentionService.
- **Desktop notification** (`core/desktop-notice.service.ts` + the app's one service worker `frontend/public/firebase-messaging-sw.js`): the operating system's own notification on the **PC screen** (outside the browser window) with the sender and the message (or "X wants to be your friend", "X accepted your friend request", "X removed the friendship"). It shows when something new arrives and the person is **not looking at the app**: the tab is hidden (another tab selected, window minimized) **or the browser window is not in front** (`document.visibilityState` hidden, or `document.hasFocus()` false). Never while the tab is in view and its window is in front. It is shown through the **service worker** (`registration.showNotification`), which Chrome and Edge handle more reliably than `new Notification` from the page (fallback to `new Notification` when no worker). **Every event has its own unique notification id** (`DesktopNotice.id`, used as the notification's tag): the message id (`message-{id}`), the request id (`request-{id}`), `answer-{connectionId}-{status}`, `removed-{connectionId}`. So a new event is never swallowed by an older notice still waiting (the first version re-used a tag per conversation and only the first one showed), and one event is announced **once**, however often it is reported (a listener restarting, the check and the live listener both seeing it). New kinds of notice must pass the id of their event. A click focuses the tab and opens the right page (the worker posts `{type:'open', url}` to the page, which navigates). If the app plays its own sound for that event the notice is silent (no double sound).
- When the browser **blocks** notifications (permission `denied`, or a refused switch), the Sound and notifications page shows an open "How do I allow notifications?" box with the steps for Chrome/Edge, Android, iPhone and Windows. A page can never change a block itself: the person allows it in the browser, then turns the switch on again.
- Sound and notifications page → Notifications: a switch that is **per browser** (`localStorage` `sf-desktop-notices` + the browser's permission, so Chrome and Edge each must be switched on), a test button, the permission state and "Last notification: ..." (shown / why it was not shown), to find out why nothing appeared. Windows must also allow notifications for the browser (Settings → System → Notifications; Focus assist off).
- "Show a test pop-up" is always active: if the switch is still off it asks for permission first, then shows the pop-up.
- A page cannot force the browser to the front (browsers forbid it); the pop-up and the title are the way to get attention.

### Setup reminder on Home
- Home shows a blue banner when **sounds** and/or **notifications** are not set up on this device, with a **Set up** button (to the Sound and notifications page) and a ✕ ("not now", hidden for this visit only: `sessionStorage` `sf-setup-hidden`, so it returns the next time the app is opened). It explains the purpose of the app: **Seven Friends is about being there for the people who matter most, and friends can only reach you if you notice them.** The same sentence opens the Sound and notifications page.
- *Sounds are set up* once the person has chosen a sound or opened the Sound and notifications page (`SoundService.defined`; opening the Sound and notifications page counts, the defaults are then kept). *Notifications are set up* when the desktop-notification switch or push is on. The banner waits until push has checked what the browser supports (`PushService.checked`), so it does not flash.

### Settings of the system (environment)
- `functions/src/settings.ts` holds the settings that can change **without touching the code**: environment variables of the backend. Put them in `functions/.env` (loaded by `firebase deploy` and the emulators; **copy `functions/.env.example`**, which lists every setting with its default; `.env` is not committed). **No secrets in `.env`**: SMS provider keys belong in Firebase secrets or `functions/.env.local`. Every setting has a default, so none has to be set; an empty value means the default; a literal `\n` is a new line.
- Settings now: `APP_URL` (the sign-up link in invitations, default `https://sevenfriends.web.app/`), `INVITE_EMAIL_SUBJECT`, `INVITE_EMAIL_TEXT` (templates with `{fromName}` `{message}` `{to}` `{appUrl}`; `{message}` is the sender's message in quotes, or empty with no hole left behind). The templates are filled in by `outbox.ts` (`inviteText`, `inviteSubject`).
- **A new text or link that someone may want to change belongs in `settings.ts` (with a default and a line in `.env.example`), not in the code.** After changing `.env`: restart the emulators / deploy the functions.
- Tests: `invitations.test.ts` (defaults, overriding, empty value).

### Sending email (your own mail server)
- `functions/src/mail-trigger.ts` is a Cloud Function (`sendMail`, Firestore trigger `onDocumentWritten` on `mail/{mailId}`) that sends every document written to the `mail` collection through **your own SMTP server** (`nodemailer`); the logic is in `functions/src/mail.ts` (`deliverMail`, testable with a fake transport). The trigger region must match the Firestore database location: set `MAIL_TRIGGER_REGION` (default `europe-west1`).
- **Settings** (`functions/.env`, see `.env.example`): `SMTP_HOST`, `SMTP_PORT` (default 587), `SMTP_SECURE` (`true` = encrypted from the start, usually 465; empty = decided by the port; 587 uses STARTTLS), `SMTP_USER`, `SMTP_PASS` (login only when a user is given), `MAIL_FROM` (the sender, e.g. `Seven Friends <noreply@yourdomain.com>`). Email is only sent when `SMTP_HOST` and `MAIL_FROM` are set; otherwise the document gets `delivery.state = "ERROR"` saying what is missing. These are plain environment variables (not Firebase secrets): keep `.env` private (it is gitignored). The password is read exactly as written (a `\n` in it is not changed), and is never written to a document or a log.
- **The result is kept in the document**, in the same format as the Firebase Trigger Email extension: `delivery: { state: PROCESSING | SUCCESS | ERROR | RETRY, attempts, startTime, endTime, error, info: { messageId, accepted, rejected, response } }`. No `delivery` = not tried yet. **A document is sent once**: the mail is claimed in a transaction, so a function that runs twice (or several at once) for the same document sends it once. An `ERROR` is not retried by itself: after fixing the settings, set `delivery.state` to `"RETRY"` in the Firestore console and it is sent again.
- A mail needs a valid `to` (an address or up to 10), `message.subject` and `message.text` or `message.html`; a bad document gets `ERROR` with the reason.
- **New dependency**: `nodemailer` (+ `@types/nodemailer`): run `npm --prefix functions install` before building. First deploy of a Firestore trigger may ask to enable the Eventarc API and take a few minutes. **The Firestore emulator runs this trigger too**: with SMTP set in `.env`, an invitation sent while developing is really sent; leave the SMTP settings empty locally to only see the document (`delivery.state = ERROR: Email is not set up`).
- **How the email looks** is set by a document: `functions/assets/mail/invite.html` (HTML, inline styles, tables; see `functions/assets/mail/README.md`). `outbox.ts` (`inviteHtml`) fills in `{fromName}` `{to}` `{message}` `{appUrl}` `{subject}` (every value escaped for HTML, so a message can never add markup), keeps the block between the two `message` comments only when the sender wrote a message, and drops the note at the top. The result goes into the mail document as `message.html` next to `message.text` (the text version, subject and link still come from the settings). `INVITE_EMAIL_TEMPLATE` points to another file; no file = text only. The files are deployed with the functions. **See it**: `npm --prefix functions run mail:preview` writes `preview.html` / `preview-without-message.html` into `assets/mail/` (not committed) to open in a browser.
- Tests: `functions/test/mail.test.ts` (sent once, settings, password never stored, html / single address, two runs at once, server failure then RETRY, not set up, bad documents, an invitation of the app).

### Push notifications (also when the app is closed)
- The phone's or computer's own notification system wakes the device through **Firebase Cloud Messaging**, so a new message, friend request, answer or removal arrives also when the app is closed or the screen is locked (the page itself cannot listen then). The device plays its own notification sound.
- **Frontend**: `core/push.service.ts` (per device, Sound and notifications → Push notifications): turning the switch on asks the browser for permission, gets the device's push token (`getToken` with the VAPID key in `environment.vapidKey`) and registers it with `POST /api/push/devices`; switching off or **logging out** removes it (`DELETE /api/push/devices`; `PushService.forgetDevice()` is called before sign-out, so the next person on the same phone gets nothing; the next login does not turn it on again by itself). Push is only available on the deployed site (not with the emulator demo project: `environment.development.ts` has an empty key) and on iPhone only from the Home Screen app.
- **One service worker** (`public/firebase-messaging-sw.js`, scope `/`; a scope can only have one): on `push` it shows the notification (data-only message: `{ id, title, body, url }`), **unless the app is in view and in front** (then the page itself shows the sound and list); `tag` = the event id, so the same event is shown once, also when the open page shows it too; on click it focuses the app and opens `url`. It caches nothing. `firebase.json` serves it with `Cache-Control: no-cache`.
- **Installable app**: `public/manifest.webmanifest` + `public/icons/` (192, 512, apple-touch) and the tags in `index.html`. iPhone only supports push for a site added to the Home Screen (iOS 16.4+).
- **Backend** (`functions/src/push.ts`): devices are `user-account/{uid}/push-device/{hash of token}` (`{ token, createdAt, updatedAt }`). A token belongs to **one account** (registering it takes it away from any other account; needs the `push-device.token` collection-group index exemption in `firestore.indexes.json`). `sendPush(uid, { id, title, body, url })` sends to all devices of the person (high priority, TTL 1 h, title ≤ 100, body ≤ 120 characters), removes tokens FCM says are gone, and **never throws** (a failing push never fails the request; it is awaited, because the function may stop after the response). Sent when: a message is written (to the receiver), a friend is added who has an account (`request-{id}`, with the message), a request is confirmed or rejected (`answer-{connection}-confirmed|rejected`, to the requester), a **confirmed** friendship is ended (`removed-{connection}`, to the other person). The ids are the same as the desktop notification's.
- Push devices are erased with the account (`erase.ts`). The push text carries the sender's name and the start of the message and passes through Google / Apple: mention this to users.
- **Setup once**: Firebase console → Project settings → Cloud Messaging: the Cloud Messaging API enabled, a Web Push key pair generated (its public key is `vapidKey` in `frontend/src/environments/environment.ts`). Deploy to Firebase Hosting (push needs https). The emulator cannot deliver pushes, so `push.test.ts` replaces `firebase-admin/messaging` with a recorder; real delivery is only checked on the deployed site. If a push never arrives: check the browser's notification permission, that the switch is on in Settings, and the function logs for "Could not send the push notification".
- Tests: `functions/test/push.test.ts` (devices register / remove / move between accounts, what is pushed for message / request / answers / removal and to whom, dead tokens removed, a failing push does not fail the request, erase removes devices).

### Signed out when the login stops working
- When Firebase Auth cannot give the signed-in person a token (`ApiService.request` asks `user.getIdToken()` before every call) because the connection to sign-in failed (`auth/network-request-failed`) or the session is dead (`auth/user-token-expired`, `invalid-user-token`, `user-disabled`, `user-not-found`), **the person is signed out** (`AuthService.forceLogout`) and sent to the login page, which shows a note: "You were signed out because the connection to sign-in failed. Please sign in again." (`AuthService.signedOutNotice`, cleared at the next successful sign-in). No error banner with Retry for this. **The same when the server answers 401 ("Invalid or expired token")**: the app asks for a fresh token once and repeats the call; a second 401 signs the person out with "You were signed out because your login is no longer valid. Please sign in again." (for example after the emulator data was reset, or a login from another project). Other errors are shown as before.
- A common cause while developing: the Auth emulator is not running (or was restarted without its data) while the browser still holds an old emulator login.

### Security: user control (`firestore.rules`)
- All data goes through the backend: it checks the login on every route and only touches the caller's own data (the Admin SDK ignores the rules).
- The app may only **read** the live data under the signed-in user's **own** account: `incoming-signal`, `messages` and my own friend list (`friend-circle/{circle}/friends`, read by its path, never by a group query). Nobody reads somebody else's, nobody reads with a collection group query, and **nobody writes from the client**, not even on their own account.
- Everything else (profiles, circles, requests) is closed to the client. A new collection is closed until a rule opens it on purpose.
- `functions/test/rules.test.ts` tests all of this against the rules engine, so it only runs with the emulator (`npm run test:emulator`, skipped in `npm test`).

### Seats and the waiting list
- **Free seat:** the request becomes a *pending seat* in their default circle (Friends page) with Confirm / Reject. Oldest request first.
- **No free seat:** the request goes on their **waiting list**, shown ONLY on the Pending page (Home shows just a count link). The requester is informed: their entry shows **Waiting** (`waitingForSeat`, "Their list is full. You are on their waiting list.").
- When a seat frees up, the oldest waiting request moves into the circle and the Waiting flag is cleared (on the next check, and right after a delete on the Friends page).
- **Mutual add** (they added each other): the two entries are merged into one connection with the shared id; no duplicates.

### One connection per pair of people
- Two people never have two connections. At the check, an entry is a **duplicate** (and is dropped from the owner's list) when the owner already has another entry linked to that person (any status), or the person already has a confirmed connection / incoming seat with the owner. Adding the same person twice, or adding someone you are already friends with, therefore ends up as one connection.
- To ask someone again after a **rejection**: delete the rejected entry first, then add again.
- If *they* then add *you* (they rejected you before), their new request replaces the old rejection: it is merged into one pending connection.
- A confirmed connection is never rewritten or merged.

### Answering a request
- **Confirm:** both entries become `confirmed` (same id, both lists), request `accepted`. Confirming with no free seat changes nothing (stays pending). This is NOT a rejection. In the app, confirming on Home opens the Friends page (where the new friend is); with no free seat you stay on Home and see the warning.
- **Reject:** request `rejected`; the requester's entry shows **Rejected** (they can see it); the recipient's pending seat is freed. A confirmed request cannot be rejected (409). A rejected request is never recreated by later checks. Rejection is not a permanent block: after deleting the rejected entry, the requester can add the person again.

- **It happens in ONE Firestore transaction** (`DELETE /circles/default/friends/:id`): all reads first, then all deletes, committed together. All of it goes or none of it.
- Delete before the other person has checked: nothing exists on their side, so only the requester's entry goes. Deleting a waiting request removes it from the other person's waiting list.

### Deleting my account (erase everything)
- **Rule: when a user is deleted, all information about that user is wiped out**: the account and profile, the login (Firebase Auth), every friendship (both entries on both sides, requests sent and received, pings), and every message they sent or received, including the other person's copy of the conversation, and every invitation email they sent (the `mail` outbox). Other people's entries that only name this person (written for their email or phone, never found yet) go too, because they hold the person's name and contact details. Whatever someone writes in a new feature that stores data about a person must be added to `functions/src/erase.ts`.
- API: `DELETE /api/users/me` with the body `{ "confirm": "DELETE" }` (400 without it, so it cannot happen by accident). Code: `functions/src/erase.ts`. Friends are not told; they just lose the friend.
- **All of it happens in ONE Firestore transaction** (all reads first, then every delete, committed together): either the person is gone from every list or nothing changed. Only the login is outside Firestore, so it is removed right after the commit; if that fails the data is already gone and the request can be repeated (it is safe to run twice).
- UI: a full-screen page `/delete-account` (reached from the red "Delete my account" card at the bottom of Profile): explains what is erased, asks to type `DELETE`, ends with Cancel / Delete everything. After success the app signs out and reloads the front page (a full reload, so nothing of the erased account stays in memory).
- Tests: `functions/test/erase.test.ts` (needs the word, removes account/entries/messages/pings/login on both sides, an unrelated connection survives, repeat is harmless, a new sign-up with the same email gets nothing, erase racing with other actions stays consistent, everybody erased leaves nothing, closing a friendship wipes everything shared).
- Needs the Firestore index exemptions in `firestore.indexes.json` (`friends.linkedUid`, `messages.fromUid`, `messages.toUid`): deploy with `firebase deploy --only firestore`.

### Messages (the feed of a connection)
- Only **confirmed** connections can exchange messages (pending, waiting, rejected or unknown friends: 403/404). The feed of a connection is identified by the connection id (the shared id of the two entries).
- A message has `time`, `fromUid`/`fromName`, `toUid`, `text` (1 to 2000 characters, trimmed) and is stored **twice**, once in each person's `messages` collection, with the same message id. The sender's copy is `read`, the receiver's copy is unread until they open the feed.
- Unread messages show up in the Home check (with their `connectionId`, so Home can open the feed). Opening the feed marks the other person's messages as read; only that connection is affected.
- The feed shows the latest 200 messages, oldest first. It is private: only the two people of the connection can read or write it.
- Deleting a connection deletes its feed on both sides.

### Profile (name, phone, social accounts)
- **Nothing on the profile may be lost** (everything autosaves): the Profile form saves about 0.8 s after the last change, when a field loses focus, **when the page is hidden or closed** (`visibilitychange` / `pagehide` / leaving the page: the request is sent with `keepalive`, so it finishes after the page is gone), and **a failed save tries again by itself every 5 seconds** and when the connection is back (`online`), besides "Try again". The same goes for the mood message and the sound choices. A save **only changes what it carries** (the backend leaves out what the request leaves out: a phone number or an account that is not in the request is kept, `null` or empty removes it), so one page can save its own part without touching the rest. A phone number that is not a valid number yet is **not sent** (the rest still saves) and the field says "This is not a phone number yet, so it is not saved". The picture, the icon, the mood and the sounds are saved by their own controls (see above); a refused value never half-saves anything.
- The **name** is editable. It can never be empty (400) and is at most 100 characters. The name from the login is only the starting point: a name the user chose **stays** at the next login.
- It is the name others see in **new** requests, pending seats and messages. Copies made earlier (a friend's list entry, old messages) keep the old name.
- **Autosave**: the page has no Save button. It saves about 0.8 s after typing stops, when a field loses focus, and when the page is left. Every save sends the whole form (`PUT /api/profile`), so saving twice changes nothing. A status line says "Changes not saved yet", "Saving", "All changes saved" or the error with "Try again" (a failed save is retried on the next change or blur).
- An empty name is not sent (the old name stays) while phone and accounts still save. An invalid value (a bad phone number) is refused and nothing is half-saved. An emptied phone or social account is removed.

### Known gaps
- The other person only sees changes when their next check runs (and the requester when the page reloads).
- Connections created before the shared id only delete on the deleting user's side.
- Live updates only reach an app that is open (the listeners run in the page); there are no push notifications. With the app closed, new requests and messages are found by the next check / the next time the feed opens.

## Media cache (images, video, audio, pictures)
Every uploaded file lives in **Google Storage** (the default bucket) as **`sf-cache/<userid>/<objectid>`**, in the folder of the person who uploaded it. Only the backend (`functions/src/sf-cache.ts`, the Admin SDK) reads and writes it; the bucket is closed to clients (`storage.rules`: no access) and **no signed URLs and no cookies** are used. The app reads a file with an ordinary API call carrying the normal login header: **`getObject(userid/objectid)` = `GET /api/sf-cache/<userid>/<objectid>`** (`<objectid>.thumb` for the small preview). The answer is the bytes of the file, its type (`Content-Type`) and its name (`Content-Disposition`), with `Cache-Control: private, max-age=31536000, immutable` and an `ETag` (a file never changes under its name; `If-None-Match` gets 304). The app shows it by fetching it with the header and making an object URL (it cannot give an `<img>` a header).
- **Kinds** (`CacheKind` in `models/shared/media.ts`; the rules are in `KIND_RULES`, ONE place for limits and formats): `image` (jpeg, png, webp, gif; 10 MB), `video` (mp4, quicktime, webm; 100 MB, bigger than 30 MB in pieces), `audio` (mp4, webm, ogg, mp3, wav; 25 MB), `avatar` (the profile picture, jpeg/png/webp, 70 KB), `icon` (a user-uploaded icon, 32 KB; **only the rules exist so far, there is no upload and no page for it yet**, it is for future use) and `thumb` (the preview of an image or video, 100 KB). **The format is found from the first bytes** (`sniff`), never from what the app says; an svg or anything else is refused (415), a file that is too big 413.
- **Message field buttons:** the image, video and voice buttons (`.sf-attach` in `chat.html`) **slide back to the left and hide while a text is being typed** (the text field grows; `max-width`, opacity and a transform, 0.25 s, no animation when the device asks for reduced motion; the hidden buttons are `inert` and `aria-hidden`), and come back when the field is empty. They are not shown at all while a message is being edited.
- **Width of media in the feed:** a message with an image, video or audio (`.sf-message-media`) is as wide as the feed allows, at most **94 % of the feed width and at most 640 px** (`--sf-media-max` in `styles.scss`, in pixels on purpose: the root font size grows on wide screens, so a `rem` limit drifted). Text messages stay at 85 %. Measured media width: 300 px at a 360 px window, 349 at 412, 518 at 600 and 631 at 1000 (the bubble has 4 px of padding on each side). Height is at most 32 rem or 70 % of the window.
- **Home, messages:** each message has the name and the **Open** / **Mark read** buttons on the first line and the text and time below over the whole width (`.sf-message-item`); these two buttons are 36 px high, smaller than the usual 44 px.
- **Media is deleted BEFORE the database rows** (single message, "delete these messages", removing a friend, erasing an account): the files (and the whole cache folder of an erased person) are wiped first, so they are gone even if the Firestore delete then fails; the request can simply be repeated. `eraseUser` does a read-only pass to find the files, deletes them, runs the real transaction, then sweeps files of messages that arrived in between (`deleteObjects` in `sf-cache.ts`).
- **No storage quota:** a person may keep any amount of images, video and audio (the 500 MB limit was removed); only the size of one file is limited (image 10 MB, video 30 MB, audio 25 MB, pictures and icons smaller).
- **Upload** (`media.ts`): `POST /api/sf-cache?kind=image|video|audio&name=<file name>` with the file as the request body (any content type except JSON; one request, at most 30 MB, because a Cloud Function takes 32 MB) answers `{ ownerId, objectId, kind, mime, name, bytes }`. `PUT /api/sf-cache/<objectid>/thumb` adds the preview of an image or video. The file name is cleaned (no folders, 100 characters).
- **Chunked upload** (for anything over the 30 MB a single request can carry, in practice video; still only through the API, no signed URLs): `POST /api/sf-cache/uploads` answers `{ uploadId, chunkBytes: 8 MB, maxChunks: 32 }` (the file will get `uploadId` as its object id); `PUT /api/sf-cache/uploads/<uploadId>/<n>` sends piece n = 0, 1, 2 … (at most 8 MB each, in any order, a piece sent again replaces the first; it is stored as `sf-cache/<userid>/tmp/<uploadId>/<n>` and counts towards the quota while it waits); `POST /api/sf-cache/uploads/<uploadId>/finish?kind=video&parts=<how many>&name=<file name>` checks that every piece is there, checks the first bytes and the total size against the kind (`checkHead`; a wrong file clears the pieces), joins them in Google Storage (`combine`, no download) and answers like a single upload (201). Finishing again after it succeeded answers the same (200), so a lost answer can be asked for again. The server keeps no state about an upload: the pieces in the folder are the state. Pieces of uploads that are never finished stay until the clean-up job is added (planned).
- **Sending:** `POST .../messages { text?, media?: { objectId, width?, height?, durationMs? } }`: a message has a text, a file or both (the text is then the caption; no text and no file is refused). The file must be one the sender uploaded and not sent yet (400 / 409). **A message with a file has the id of its file** (so a file is in one message only, and the receiver is let in by looking for the message with that id: no extra index). Both copies of the message hold `media` (`MediaRef`: ownerId, objectId, kind, mime, name, bytes, width, height, durationMs, hasThumb), the feed returns it as `ChatMessage.media`, Home and the push notification say "📷 Photo", "🎞 Video" or "🎤 Audio" when there is no text. The caption can be edited; the file cannot.
- **Who may read** (`mayRead`): the owner (always); the person a message with that file was sent to (they have the message); for an `avatar` the owner's confirmed friends. Anything else, also an unknown object, is **404**, so nobody can find out what exists.
- **Cleanup:** deleting a message (one, or clearing several, also the friend's messages when "both") deletes its file and preview; removing a friend deletes the files of the conversation; erasing an account deletes the files of all its conversations and the person's whole folder; replacing or removing a profile picture deletes the old object. (Files uploaded but never sent, and pieces of unfinished uploads, stay until a clean-up job is added: planned.)
- **App side, images (built):** the image icon in the message field opens `/friends/:id/image`. `core/image.ts` (`prepareImage`) makes the chosen image ready **in the browser**: scaled down to 1600 px and saved as a JPEG (the position and other details inside a photo are left behind, a transparent picture gets a white background) plus a 320 px preview; a GIF is sent as it is (up to 10 MB), so it keeps moving. `MediaService.uploadImage` sends the file with its name (`POST /api/sf-cache?kind=image&name=...`), then the preview (`PUT .../thumb`); then `ChatService.send(friendId, caption, { objectId, width, height })` sends the message with the reference (an upload that worked but whose message failed is not uploaded again on the next try). The page then goes back to the conversation, **which reads the message and the image back from the server**: the feed shows `app-media-image`, which calls `getObject` (`MediaService.object`, `ApiService.file`: a normal API call with the login header; the bytes become an object URL; the small preview is used when there is one) and keeps what it read for as long as the app is open (a file never changes under its name). A friend's image opens the viewer when tapped; on my own message the tap opens Edit / Delete as for any message of mine, with an extra **Open** button (Edit changes the caption). **The camera** works on every device in one of two ways (`add-media.ts`, `camera/camera.ts`): on a **phone or tablet** (found from the system in `navigator.userAgent`: Android, iPhone, iPad, and an iPad that says it is a Mac; **not from a touch screen**, because a Windows laptop with a touch screen has one too and `capture` does nothing there, so "Record a video" only opened the file chooser) "Take a photo" is a file chooser with `capture="environment"`, which opens the **camera app of the phone**; on a **computer** (Windows, Linux, Mac, with or without a touch screen) the browsers ignore `capture`, so "Take a photo" shows the camera **on the page** (`getUserMedia`, a full-screen view, not a pop-up) with **Take the photo** (the frame is drawn to a canvas and saved as a JPEG file) and **Use another camera** when the computer has more than one; the view is mirrored, the photo is not, and the camera is stopped (the light goes out) when the page is left. The button is not shown when the browser has no camera API (it needs https or localhost). A blocked, missing or busy camera says so and leaves "Choose an image". A photo then goes the same way as a chosen picture. Shared helpers: `decodeImage` / `sizeOf` (also used by the profile picture page), `formatBytes`.
- **App side, video (built, up to 30 seconds):** the video icon in the message field opens `/friends/:id/video` (same page as images, `add-media`). **Length:** at most **30 seconds** (`MAX_VIDEO_SECONDS` in `core/video.ts`). A recording stops by itself at 30 s (the page shows `● 12 / 30 s`); a chosen file that is longer is **cut to its first 30 seconds** and the page says so. **Compression, in the browser** (`prepareVideo`): the video is played into a canvas and recorded again with `MediaRecorder` (`canvas.captureStream` plus the sound through WebAudio): at most **1280 px** on the long side, about **1.2 Mbit/s** video and **96 kbit/s** sound, as **MP4 with H.264 and AAC** where the browser can record exactly that, otherwise **WebM (VP9/VP8 and Opus)**; a bare `video/mp4` is never used because a browser may then put Opus sound in the MP4, which many players (Safari, Windows) play silently. The recording listens along (`AnalyserNode`): if it caught no sound at all and the original is a file the server keeps (mp4/webm/quicktime, not cut, under 100 MB), **the original is sent** instead of the silent copy. Measured: 8 s of 1080p (8 MB) became 0.7 MB. The work runs in real time (about as long as the video, shown as a percent) and the page must stay visible. If the browser cannot recompress, a file that is already mp4/webm/quicktime, not cut and under 100 MB is sent as it is, otherwise the page says so. A preview picture (320 px JPEG) is made and sent with `PUT .../thumb`. **Camera:** a phone uses `<input capture="environment" accept="video/*">` (the camera app); a computer shows `app-camera` (`mode="video"`, `getUserMedia` with sound; **the preview element is muted through its `muted` property and volume 0 in code, because the `muted` attribute alone does not mute an element Angular creates, and the microphone would be played from the speakers and heard again (feedback)**; the voice recorder has no player and its level bar is not connected to the speakers, **Start recording** / **Stop**, **Use another camera**; the tracks are stopped when the page is left). **Upload:** `MediaService.uploadVideo` uses one `POST /api/sf-cache?kind=video` when the file is at most 8 MB and otherwise the **chunked upload** (`/sf-cache/uploads`, pieces of the size the server answers, `finish`), with a progress text; the message then carries `{ objectId, width, height, durationMs }`. **In the feed** `app-media-video` shows the preview with a play button and `m:ss · size`; **the video itself is read from the server only when play is pressed** (`getObject`, kept for the session). Caveats: the recorded WebM has no length or seek information in its header (the player may not show a length until the end); not tested on real phones, Safari or iPhone; the MP4 path needs a browser that records H.264. Tested in Chromium with a fake camera (record, choose, 35 s cut, wrong file, phone `capture`, 4-piece chunked upload) against a mock server.
- **App side, audio (built, voice messages):** the microphone icon in the message field opens `/friends/:id/audio` (same page as images and video, `add-media`). **Recording** is always on the page (`app-voice`, `voice/voice.ts`, on computers and phones alike, because the file chooser of a phone cannot record audio everywhere; needs https or localhost): **Start recording** / **Stop**, the time `0:12 / 2:00`, the **name of the microphone in use**, and a **level bar** that moves with the voice (so it is seen that the microphone works; `AnalyserNode`). **The recorder also says when the microphone is muted**: the browser marks the track as muted (`MediaStreamTrack.muted`, with the `mute` / `unmute` events, so it is followed live) when Windows, the driver, a mute key or a privacy setting mutes it, and a red message with where to unmute it is shown until it is unmuted. **A recording in which nothing at all was heard (loudest moment under about -40 dBFS) is not kept**: the recorder says so and stays open, and **Use another microphone** (shown when the computer has more than one) switches, because the default microphone of a computer may be muted or not the one that is plugged in. The microphone is first opened with the browser's own settings (`audio: true`, or the chosen `deviceId`: echo cancelling, noise cutting, automatic gain). **Some microphones give only silence with those filters on (the "Microphone Array" of Realtek on Windows, seen on a real machine)**: when a recording is silent, the microphone is opened again **without the filters** (`echoCancellation`, `noiseSuppression` and `autoGainControl` false), the person is told to record once more, and the choice is remembered (`localStorage` key `sf-mic-raw`, per browser). Silent again without the filters shows the "nothing was heard" warning. The players show "This device cannot play this audio" when the browser cannot decode the file. It records mono at **32 kbit/s** straight into a small file (`core/audio.ts`: AAC in MP4 where the browser records `audio/mp4;codecs=mp4a.40.2`, otherwise Opus in WebM or Ogg; a bare `audio/mp4` is never used) and **stops by itself after 2 minutes** (`MAX_AUDIO_SECONDS`); 2 minutes are about 0.5 MB. A blocked, missing or busy microphone says so and leaves "Choose an audio file". **A chosen audio file is sent as it is** (not played again to make it smaller, that would take as long as the audio): at most **2 minutes** (the length is read from the file; a longer one is refused, it is not cut) and **25 MB**; the server checks the real type (mp3, m4a/mp4, wav, ogg, webm). **Upload:** `MediaService.uploadAudio` (one `POST /api/sf-cache?kind=audio`, or the chunked upload over 8 MB; no preview picture); the message carries `{ objectId, durationMs }`. **In the feed** `app-media-audio` shows a play button with `m:ss · size` and the **⤓** button to the viewer; **the audio is read from the server only when play is pressed** (`getObject`, kept for the session). The viewer plays audio and has **Download**. Caveats: the length of a recorded WebM is not in its header (the page finds it by going to the end); not tested on real phones, Safari or iPhone. Tested in Chromium with a fake microphone (record with level bar, choose mp3 and wav, 150 s refused, a picture refused, blocked microphone, play from the server, viewer and download, phone layout).
- **Not built yet:** slicing a big file into pieces in the app (video), the app side for video and audio, voice recording, the clean-up job, and any use of `icon`.
- **Setup:** Firebase Storage must be enabled for the project (it needs the Blaze plan, which Functions need anyway) and `npm run dev:emulators` starts the Storage emulator too (port 9199). Deploy the rules with `firebase deploy --only storage`. The function reads the default bucket from the project settings (`initializeApp()`); check this against the real project and the emulator, it is not covered by the tests (they use an in-memory bucket, `test/fake-storage.ts`).

## Conventions
- **All interfaces and types live in a `models` folder**, never inside a service, component or router file. Import them from `./models` (backend) / `../models` (frontend).
- **The API types are written once and copied into the frontend.** The source is `functions/src/models/shared/` (Friend, FriendRequest, Circle, Message, ChatMessage, Conversation, Socials, ... everything that crosses the API). `scripts/sync-models.mjs` copies it to `frontend/src/app/models/shared/` before every `npm start` / `npm run build` / `npm test` in the frontend (npm pre-hooks), and by hand with `npm run sync:models`. The copy is generated and not committed (gitignored): **never edit it, edit the source**. Nothing is shared as a module; each project compiles its own copy.
  - A shared model holds **types only** (no `const`, function, class or enum) and imports only from its own folder (`./`). The script refuses anything else (backend packages do not exist in the frontend), and `functions/test/shared-models.test.ts` guards it.
  - Backend-only types stay in `functions/src/models/` (`seats.ts`, `outcome.ts`); frontend-only types (page / form types) in `frontend/src/app/models/` (`view.ts`, `social.ts`). The backend routes are typed with the shared models, so a change to an API shape fails to compile on the backend and, after the copy, on the frontend.
  - If you run `ng serve` / `ng build` directly (not through npm), run `npm run sync:models` first. `npm run check:models` (project root) fails if the copy is out of date.
- Angular 20 (pinned because the dev machine runs Node v22.14.0; do not upgrade to Angular 21+ without upgrading Node to >= 22.22.3).
- **Never inject the `Router` straight into a core service that the Router itself depends on.** The Router needs the title strategy, which needs `AttentionService`, which needs `MessagesService`, `FriendsService` and so `ApiService`: `ApiService` injecting `Router` is a circular dependency (NG0200) that builds fine but leaves a **blank page**. Fetch it when needed with `inject(Injector).get(Router)` (as `ApiService` does). A build does not catch this: open the app after changing what a core service injects.
- Standalone components only, no NgModules. Prefer signals and the new control flow (`@if`, `@for`).
- Backend routes live under `/api` and must be reachable through Hosting rewrites.

## Login methods and console setup
- Phone sign-in (per the Firebase guide): `localhost` is **not allowed** for real SMS (use the emulator, whose log prints the code with the reCAPTCHA check switched off, or up to 10 **fictional test numbers** with fixed codes under Authentication → Sign-in method → Phone → "Phone numbers for testing"). The deployed domain must be under Authorized domains. Phone alone is less secure than the other methods (a number can change hands), so it is offered next to Google / email; the phone page tells people that a text is sent and message rates may apply.
- Google, email/password, email link, phone SMS. People are reachable by their email or phone even when unverified; their friends are told (see People who have not verified).
- **Nobody has to be verified to add a friend or to be added.** Verification only decides what the other side is told (see People who have not verified). A phone login has no email and is confirmed by the SMS code; Google and email-link logins arrive with a verified email. The account document keeps `emailVerified` and `verifiedPhone`, written from the login token at every login, and `GET /profile` returns `emailVerified` / `phoneVerified`. The Verify buttons only appear for what is not verified yet.
- Firebase console: Authentication → enable **Google**, **Email/Password** (with **Email link** switched on) and **Phone**; add your domain under Authorized domains. Phone sign-in needs the **Blaze plan**, costs per SMS, and SMS region policy should allow your countries.
- Emulator: reCAPTCHA is disabled and SMS codes are printed in the auth emulator log; email links are printed there too.
- After backend changes: `npm --prefix functions install`, restart emulators, `firebase deploy --only firestore` (rules and indexes), then deploy functions.
- Known gap: email-link, SMS and rules tests are not automated in the cloud (needs the emulator); they are build-verified only.
- **Never write `firestore.rules` in place while the emulator runs** (a truncating write can be read as an empty file; the emulator then fails every database request with "Rules content empty"). Save the file in one step; if it happens, save the file again and look for "Rules updated" in the emulator log.

## Sleep list

## Several devices at once (live sync of my own changes)

- **Friend list** (add, delete, sleep, trust, confirm ...): my entries are listened to (`RealtimeService.watchFriends`), any change reloads the list on every device.
- **My messages** (send, edit, delete, "delete these messages"): the backend also stamps `messagesChangedAt` on MY entry of the friendship, so my other devices reload that open feed (`feedChanged`), like they do for the friend's edits.
- **One place each:** backend: every "tell the other devices" write is in `functions/src/sync.ts` (`touchSync`, `touchFeed`, `touchFeedIfExists`, `tellFriendAsleep`), never a stamp written by hand in a route. App: `RealtimeService` is the only one that listens to Firestore; it emits `LiveChange` events on `LiveChanges` (`core/live-changes.ts`: `profile`, `sounds`, `feed`) and each service/page subscribes to its kind with `live.on('feed')` etc. (`takeUntilDestroyed`). The friend list is reloaded by `RealtimeService` itself (it needs the before/after to announce answers).
- **Profile and sounds:** the backend stamps `user-account/<uid>/sync/state` (`touchSync` in `functions/src/sync.ts`: `profileAt` on every profile change incl. mood and picture, `preferencesAt` on sounds). The app listens (`RealtimeService.watchSync`, rules allow reading `sync/*` for the owner): `profileChanged` makes the mood editor and the Profile page (picture, icon, verification, NOT the form being typed in) reload; sounds are reloaded by `SoundService.reloadFromAccount()` unless a change of mine is waiting to be saved. The stamp document is deleted when the account is erased.
- Needs `firebase deploy` (functions AND `--only firestore:rules` for the new rule). Not tested with two real devices; no backend tests for the stamps yet.

## UI preferences (one object in localStorage)

- `core/ui-preferences.ts` (`UiPreferencesService`) holds EVERY local choice in ONE object under the key `sf-ui`: `chatOrder` (oldest/newest first), `lastPage` (shown again when the app is opened at `/`; set on every navigation to a main page or a conversation, cleared at sign-out) and `micRaw`. Read with `prefs.get('key')` / `prefs.value('key')` (a signal), write with `prefs.set('key', value)`; **never use localStorage directly for a choice**: add the field to `UiPreferences`, `DEFAULTS` and `read()`. Other windows follow through the `storage` event; the old keys `sf-chat-order` and `sf-mic-raw` are read once if the object does not exist yet.
- Not in it on purpose: the sounds (an account setting, `SoundService`, synced between devices), the "delete these messages" filter (always starts safe), the "setup hidden" note (per session), login/push/desktop-notice keys (device and account state).

## Links in messages (clickable, with a page preview in a frame)

- A web address in a message text is a link (`parts()` in the Chat page: opens in a new tab with `rel="noopener noreferrer nofollow"`; only http/https).
- **Preview = the real page in a frame, not a picture.** When a message is sent or edited, `linkOf()` (`functions/src/link-preview.ts`) takes the FIRST address and stores `link: { url, embedUrl }` on both copies of the message (`MessageLink` in the shared models; `FieldValue.delete()` when an edit removes the link). `embedUrl` is the official player for YouTube / Vimeo / Spotify links (`playerUrl`), otherwise the page itself IF the site allows framing: the server asks the site once (GET, headers only, 3 s) and refuses when `X-Frame-Options` is set or `Content-Security-Policy: frame-ancestors` does not contain `*` / `https:` (`framingAllowed`); other content types (pictures, files) and any error give `embedUrl: null` (just a link). It never fails the message.
- **The feed shows "Show preview" and loads the page only after a tap** (it exposes the reader's address to that site and runs its scripts). The `iframe` is sandboxed (`allow-scripts allow-same-origin allow-forms allow-presentation`, no pop-ups, no top navigation), `referrerpolicy="no-referrer"`, with "Open in a new tab" and "Hide preview". Sites that forbid framing (Google, Facebook, X, most news sites, banks) only show the link.
- **SSRF protection** (the server fetches a typed address): http(s) only, ports 80/443, no password in the address, the connection uses our own DNS lookup that refuses private / loopback / link-local / metadata addresses at connect time (also after redirects, max 3), the body is never read. Tests: `functions/test/link-preview.test.ts` (pure parts, verified; the live fetch is not tested).
- Not done: a JavaScript "frame buster" on a page cannot be detected; a page that allows framing but shows a blank frame stays blank (use "Open in a new tab"); no check of the site's own CSP `frame-src` for our hosting (none is set).
- Needs the backend deploy (functions) and hosting.
- **Preview while writing:** the message field looks for a link a moment (700 ms) after the last key press and asks `POST /api/link-preview { text }` (`linkPreviewRouter` in `link-preview.ts`, login needed, 20 asks per person per minute, then 429) which answers `{ link }` with the same check as at send time. A bar above the field shows the address and "Show preview" (the page is loaded only after a tap) or "No preview: the site does not allow it", with ✕ to close it (the same link does not come back while it stays in the text). It is only a convenience: the server checks again when the message is sent. Needs the backend deploy.
- `npm run deploy` deploys everything (functions, Firestore + Storage rules, hosting); `deploy:hosting`, `deploy:functions`, `deploy:rules` deploy one part.

## Friend links
`/?invite=<code>` (the code is made on the server, `functions/src/invite.ts`; the profile page has Share / Copy / New link) or `/?friend=<email or phone>`.
`FriendLinkService.capture()` runs in an app initializer (before the router can redirect), keeps the link in UiPreferences (`pendingFriend`) and removes
it from the address bar. Signed in + a link waiting -> `app.ts` sends every navigation to `/friends/join` (`friend-join/`), which asks "Send a friend
request to …?" (nothing is sent without the tap) and then uses the ordinary `friends.add()`. Signed out: the login page says what the link is about.
A new code makes the old link stop working. `FieldValue.delete` is supported by the test fake (`functions/test/fake-firestore.ts`).
A friend link whose owner has ALREADY sent me a request (`requestId` from `/invite/lookup`, or the request's `fromEmail` for plain links) shows that
request with "Confirm request" instead of the form: no second request is made. The join page first runs `notifications.refresh()`.
`InviteLinkService` (core/invite-link.service.ts) holds my link and the Share / Copy / New link buttons: used by the profile page and by Add a friend
(there the link card appears as soon as an email or phone number is typed; "Send the link to them" is disabled on purpose: not built yet).
The Home page has an expandable card ("Invite people with a link") under the band: the plain friend link `/?friend=<my email or phone>` with Share / Copy and a short explanation.

## Pictures and memory
A phone photo can be 50 million pixels. `decodeImage` (core/image.ts) reads the size and the position note (EXIF) from the first bytes and asks the browser to make
the picture small WHILE decoding it (never the full picture first); `prepareImage` makes the preview from the small picture and empties its canvases at once.
Do not decode a chosen photo at full size anywhere.
